# 远程视频帧协议 v2

## 1. 物理层

| 项 | 值 |
|---|---|
| 串口 | USART1（PA9/PA10）→ 板载 CH340 → PC COM22 |
| 波特率 | **1,500,000**（8N1） |
| 流控 | 无 |
| 发送方式 | USART1 TX DMA（DMA1 Channel4），不阻塞 LCD 刷新 |
| 本地显示 | 320×240 RGB565，约 9–10fps |
| 远端图像 | 320×240 中心裁剪 **192×144**，RGB332（8 位色） |

> 注意：板载 CH340 在 2Mbaud 下会丢字节，实测有效帧率反而降到 1.5fps；1.5Mbaud 是可靠上限。

## 2. 帧格式

| 偏移 | 长度 | 内容 |
|---|---|---|
| 0 | 2 | 帧头 `0xAA 0x55` |
| 2 | 4 | payload 长度，**小端**（192×144 = 27648 = `0x00006C00`） |
| 6 | 2 | 校验和，小端：payload 所有字节按 uint16 累加（mod 65536） |
| 8 | N | payload：RGB332 像素，逐行从左到右、从上到下 |

- 单帧总长 = 8 + 27648 = **27656 字节**。
- 校验和计算：`sum = (sum + byte) & 0xFFFF`。
- PC 端校验失败直接丢帧并重新找帧头，避免错位帧上屏。

## 3. RGB332 定义

每个字节：

```
bit7..5  R3
bit4..2  G3
bit1..0  B2
```

PC 端调色板：

```python
r = ((v >> 5) & 0x07) * 255 // 7
g = ((v >> 2) & 0x07) * 255 // 7
b = (v & 0x03) * 255 // 3
```

## 4. 参数取舍（实测）

| 分辨率 | 色深 | 波特率 | payload | 实测有效帧率 | 结论 |
|---|---|---|---|---|---|
| 160×120 | RGB332 | 1.5M | 19,200 | 4.3fps | 快，但手机上看很糊 |
| 240×180 | RGB332 | 1.5M | 43,200 | 2.3fps | 清晰些，但低于 3fps |
| 240×180 | RGB332 | 2M | 43,200 | 1.5fps | CH340 丢字节，不可用 |
| 200×150 | RGB332 | 1.5M | 30,000 | 3.1fps（未校验）/2.6fps（校验后） | 有偶发错帧 |
| 200×150 | RGB332 | 1M | 30,000 | 2.3fps | 链路稳定但 UART 时间太长 |
| **192×144** | **RGB332** | **1.5M** | **27,648** | **3.0fps** | **最终选择** |

## 5. 为什么不是 STM32 端 JPEG

- F103 只有 64KB RAM；QQVGA RGB888 缓冲约 57.6KB，jpge 还需要输出缓冲，很难同时放下 FIFO 读帧/显示/编码。
- 当前方案把 JPEG 编码放到 PC 中继，STM32 只发 RGB332；带宽/内存都可控，手机端仍然是标准 JPEG。
- 后续换 ESP8266/ESP32 时，协议不变，只需把 PC 中继的串口侧换到 WiFi 模块。

## 6. 测试命令

```bash
curl "http://127.0.0.1:8000/status?t=1"
curl -o snapshot.jpg "http://127.0.0.1:8000/snapshot.jpg?t=1"
```

`/status` 返回 `serial_frames`（有效帧数）、`checksum_errors`、`fps`、`resolution`，可用于报告中的吞吐/丢帧统计。
